# SOC 2

SOC 2 (Service Organization Control 2) is the de facto enterprise-SaaS
trust certification in the US. If MemberClub wants to sell to companies
whose procurement asks "do you have a SOC 2 report?", the answer needs
to be yes, with the report attached.

This file is what an engineer needs to know to (a) understand what's
being audited, (b) point to the evidence in this repo when an auditor
asks, and (c) not get a finding for something that's actually fine.

## Type I vs Type II

- **Type I** is a point-in-time report: "as of date D, the company has
  these controls in place." Less expensive, faster to obtain. Often the
  first one a startup gets.
- **Type II** is a period-of-time report: "over the audit window
  (typically 6 or 12 months), the controls operated effectively." This
  is what enterprises actually want. The auditor takes samples across
  the window and verifies that the control worked every time.

Most procurement processes will accept Type I for a first engagement
and then require Type II within the following year. Plan accordingly.

The practical difference for engineering: **Type II means evidence
collection is a continuous discipline, not a quarter-end scramble.**
Every PR that bypasses code review, every prod change without a ticket,
every alert that didn't get acknowledged — each is a Type II failure
if it falls in the sample.

## The five Trust Service Criteria (TSC)

SOC 2 reports cover one or more of five "criteria":

1. **Security** — the only mandatory one. Defenses against unauthorized
   access (logical and physical). Almost everything in
   [`docs/security/`](../security/) maps here.
2. **Availability** — the system is up and accessible per its commitments.
   Disaster recovery, capacity planning, monitoring.
3. **Processing Integrity** — the system processes data completely,
   accurately, in a timely manner, and as authorized. Idempotency,
   exactly-once semantics, transactional correctness.
4. **Confidentiality** — confidential data (defined by the customer
   relationship, often broader than PII) is protected.
5. **Privacy** — PII is collected, used, retained, disclosed, and
   disposed of per the privacy notice. Overlaps heavily with GDPR.

Startups typically scope their first SOC 2 to just **Security** plus
maybe **Availability**. Adding criteria adds audit cost and engineering
work; do it when a customer specifically requires it.

## What an auditor will actually ask for

For each TSC, the audit framework breaks down into ~50–100 controls.
The auditor's job is to verify that each control exists, is documented,
and (for Type II) was followed during every sample they took. The
controls cluster into a few areas.

### 1. Change management

"How do you ensure code changes to production are reviewed, tested,
and authorized?"

**Evidence to point at:**

- The GitHub PR template (`.github/PULL_REQUEST_TEMPLATE.md` or similar)
  showing required fields.
- The `CODEOWNERS` file showing required reviewers.
- The CI workflow files showing required checks (build, test, lint,
  security scan).
- The branch protection settings on `main` (require PR, require
  reviews, require status checks). Auditor will ask for a screenshot
  or repo-settings export.
- Sample PRs from the audit window: chosen randomly by the auditor,
  must show review approval, passing CI, no force-push to main.

**Common findings to avoid:**

- A maintainer pushed directly to `main` outside the PR flow.
- A PR was merged with failing CI (this is detectable from GitHub's
  history; don't do it).
- A reviewer approved their own PR.

### 2. Access control

"Who has access to what, how is it provisioned, how is it revoked?"

**Evidence to point at:**

- [`projects/04-auth-demo`](../../projects/04-auth-demo/) and
  [`projects/05-rbac-policy-lab`](../../projects/05-rbac-policy-lab/)
  document the authentication and authorization model.
- The production access list: SSO group membership, database user
  roster, cloud-IAM role assignments. Reviewed quarterly.
- Offboarding checklist: when an engineer leaves, every credential is
  rotated or revoked within 24 hours. Auditor will sample offboarded
  employees from the window and check.
- MFA enforcement on every privileged account.

**Common findings to avoid:**

- Shared accounts (`admin@`, the database `postgres` superuser used
  by humans).
- Standing access to production for engineers who don't need it
  (use break-glass with auditable approval flow instead).
- A long-tenured engineer's GitHub access wasn't revoked when they
  switched teams away from MemberClub.

### 3. Monitoring and logging

"How would you know if something bad happened?"

**Evidence to point at:**

- The Prometheus/OpenTelemetry stack (covered by sibling docs in the
  observability track).
- The `audit_log` table in MemberClub — every state-changing admin
  action recorded with actor, action, target, before/after, timestamp.
  This is the table the auditor will spot-check most thoroughly.
- Alert routing: how a 5xx spike on a Saturday at 3am gets a human
  on the phone. The on-call rotation, the paging tool's history.
- Log retention: how long logs are kept, where, with what access
  controls. Usually 90 days hot, 1 year cold.

**Common findings to avoid:**

- Alerts go to a Slack channel that nobody monitors after hours.
- The `audit_log` table is missing rows for some classes of admin
  action (the `UpdateUserRole` endpoint forgot to log).
- Logs contain PII that the privacy notice didn't disclose.

### 4. Incident response

"What do you do when something does happen?"

**Evidence to point at:**

- [`docs/runbooks/`](../runbooks/) — the operational playbooks.
- [`docs/03-postmortems/`](../03-postmortems/) — actual postmortems
  from real incidents in the audit window. The 5xx-spike postmortem
  there is the canonical example.
- The post-mortem template at
  [`docs/03-postmortems/0000-TEMPLATE.md`](../03-postmortems/0000-TEMPLATE.md).
- The incident-severity definitions (Sev1/Sev2/Sev3 thresholds).
- Status-page entries cross-referenced to internal incidents.

**Common findings to avoid:**

- An incident in the window has no postmortem.
- Postmortems exist but action items have been open for months without
  progress.
- The runbooks reference tools or commands that no longer exist.

### 5. Risk assessment

"How do you decide what risks to mitigate?"

**Evidence to point at:**

- [`docs/security/01-stride-threat-model.md`](../security/01-stride-threat-model.md)
  is the formal threat model. Reviewed at least annually.
- The risk register (a spreadsheet/Notion doc listing identified risks,
  likelihood, impact, mitigation, owner). The threat model feeds it.
- Penetration test reports (external).

### 6. Vendor management

"How do you assess the security of the third parties you depend on?"

**Evidence to point at:**

- The subprocessor list (also required by GDPR; see
  [`01-gdpr.md`](./01-gdpr.md)).
- A vendor security review for each new subprocessor: their SOC 2
  report or equivalent, the DPA, the security questionnaire.
- [`docs/security/03-supply-chain.md`](../security/03-supply-chain.md)
  covers the open-source dependency angle.

### 7. Data backup and recovery

"If your database burns down, how do you get back?"

**Evidence to point at:**

- [`docs/runbooks/disaster-recovery.md`](../runbooks/disaster-recovery.md)
  — the runbook, the RPO/RTO targets, the backup strategy.
- Restore-test reports: the auditor will ask "when did you last
  restore from backup and verify it worked?" Annually is the minimum
  acceptable answer.
- Backup access controls: only specific roles can read backup buckets.

## The evidence-collection workflow

Type II audits do not happen in a week. They happen continuously,
through tooling and discipline.

The mechanical pieces:

1. **Compliance platform** (Vanta, Drata, Secureframe, ...) connects
   to GitHub, AWS, Okta, Datadog, etc. and continuously snapshots state.
   It alerts on drift (a new IAM user without MFA; a branch protection
   weakened; a PR merged without review).
2. **Quarterly access reviews**: each owner reviews their domain's
   access list, marks anything that shouldn't be there for removal,
   signs off. The signed reviews are evidence.
3. **Annual policy review**: each written policy (security, incident
   response, change management, ...) gets re-read, updated, and
   re-signed by the security owner.
4. **Continuous monitoring of in-window events**: every PR, every
   incident, every offboarding gets captured in the evidence trail
   as it happens.

Engineering's day-to-day involvement is mostly:

- Follow the change-management process (every change is a PR with review
  and passing CI).
- Write the postmortem when something goes wrong.
- Don't share credentials.
- Don't bypass MFA.
- Don't push directly to `main`.

If those five behaviors are universal, ~80% of SOC 2 takes care of
itself.

## Common SOC 2 traps engineers fall into

- **"It's documented" ≠ "we do it."** The auditor will sample. If your
  policy says "every PR requires two reviews" and you have a PR in the
  sample with one review, that's a finding regardless of what the
  policy says.
- **"Best effort" isn't a control.** "We try to monitor failed
  logins" is not a control. "Failed logins are alerted via PagerDuty
  with a 5-minute response SLA" is a control.
- **Tools you no longer use still count.** If three years ago you set
  up a Sentry account that's been collecting dust, and a customer's
  exception data is still in it, it's in scope. Audit your tool
  inventory periodically and decommission dead tools properly.
- **Sub-services count.** If you use a fly.io worker that handles
  customer data, fly.io is a subprocessor.
- **Test environments leak.** If you copy prod data to staging for
  testing, staging is now in scope. The standard fix is synthetic data
  for staging.

## Reading a SOC 2 report you receive from a vendor

When a third party gives you their SOC 2 report:

1. Check Type I vs Type II. Type I is much weaker.
2. Check the audit window. A Type II from 2023 doesn't tell you about
   today.
3. Check the scope: which TSCs are covered? "Security only" is
   different from "Security, Availability, Confidentiality."
4. Check the exceptions and findings. The "Independent Service Auditor's
   Report" section names anything the auditor flagged. Vendors will
   downplay these; read them yourself.
5. Check the **Complementary User Entity Controls** (CUECs). These are
   things the vendor expects you to do; if you don't, their controls
   don't fully protect you. E.g. AWS's CUECs include "the customer is
   responsible for managing access to their own resources."
